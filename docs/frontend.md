# Frontend: запуск и передача команде

Реализованы экраны входа, каталога с планом, сводки дня, статистики и администратора (люди, отделы, настройки). UI русский, адаптивный, с бумажным фоном и шалфейным акцентом. На телефоне каталог и план переключаются вкладками.

## Локальный запуск без backend

Из `frontend/` (Node.js 22.13+ или 24):

```bash
npm ci
npm run dev
```

Открыть `http://localhost:5173`. Внизу формы входа есть кнопки четырёх демо-учёток. Обычная кнопка «Войти» всегда вызывает реальный API; автоматического перехода на моки при ошибке нет.

Демо доступно в Vite dev. В production оно выключено; для отдельной учебной сборки можно явно задать `VITE_ENABLE_DEMO=true` при сборке. Демо не является авторизацией или заменой backend. Пароли реальных пользователей в демоданные не сохраняются.

Учебные планы, пользователи, отделы и настройки хранятся в `localStorage` под `corplunch.demo.v1`. Текущая демо-учётка — в `sessionStorage`. Выход сохраняет планы для следующего сотрудника; «Сбросить демо» удаляет учебные изменения после подтверждения. Созданные в демо пользователи демонстрируют админский CRUD; вход поддерживается только четырьмя исходными демо-учётками, пароль в демо не изменяется.

Дата по умолчанию — послезавтра по Москве, чтобы демонстрация оставалась редактируемой и после сегодняшнего cutoff. Можно выбрать другую дату. Для сводки двух людей используйте один браузер и последовательно выходите/входите. Разные профили браузера не разделяют локальные демоданные.

В демо при закрытии дня ньокки дорожают на 15 ₽, салат становится недоступен. Это предсказуемый учебный сценарий, а не текущие цены Mealty. Карточки содержат учебные SVG-иллюстрации; настоящий API может вернуть `image_url`.

## Подключение реального backend

Календарь показывает дату доставки и текущую сумму состава; на телефоне состав открывается вкладкой «Мой план». Заголовок состава — «План на среду» (по выбранному дню). Рост и снижение цены относительно `planned_price_kopecks` отмечаются охрой с указанием старой и новой цены. В черновике сравнивается цена каталога, после расчёта — `actual_price_kopecks`; снятое блюдо показывает «Нет в меню Mealty».

Редактирование определяется только `editable` из ответа плана. Срок приёма сотруднику не показывается; настройки для этого не запрашиваются. Активная страница опрашивает план каждые 10 секунд, включая несохранённый черновик: пока день открыт, локальный состав сохраняется, после закрытия отображается сохранённый сервером состав. Задержка блокировки UI — интервал опроса плюс время запроса; сервер отклоняет сохранение после cutoff независимо от UI. Ошибка `403 / Cutoff passed` отображается как «Приём заказов на эту дату закрыт. Изменить состав уже нельзя.».

Vite проксирует `/api` в `http://localhost:8000`; Compose задаёт `API_PROXY_TARGET=http://api:8000`. Введите почту и пароль и нажмите «Войти». Токен передаётся только в `Authorization: Bearer`, запросы используют `credentials: omit`. При 401 токен и кэш сессии очищаются.

Контракт централизован в `src/api.ts`, DTO — `src/types.ts`, серверное состояние — TanStack Query. Моки реализуют тот же интерфейс `AppApi` в `src/demo.ts`. После стабилизации backend OpenAPI заменить ручные DTO/пути генерацией. Календарь работает с реальными API каталога и планов; админка — с API пользователей, отделов и настроек.

Ограничение прав на frontend управляет навигацией; обязательная серверная проверка ролей остаётся ответственностью backend. Админ не редактирует чужие планы. Закупки читают состав сотрудников через `GET /plans/{date}?user_id=`.

Статистика использует только поля текущего `GET /stats/summary`: суммы, отделы, сотрудники, топ блюд, изменения цен. Визуализация — расходы по отделам. Данных по отдельным дням в контракте нет, поэтому график по дням не подменяется выдуманными значениями. Список отделов фильтра берётся из нефильтрованной статистики за период: закупки не вызывают admin-only `/admin/departments`.

При работе с API CSV/XLSX скачиваются с сервера как Blob. Только деморежим создаёт локальные файлы с контрактными колонками; XLSX — настоящий OOXML-архив с листом «По сотрудникам».

## Проверки

Live-проверки используют основной Compose с `tests/.env.test`. Запуск изолированного стенда и серверного регресса описан в [tests/README.md](../tests/README.md).

Админка загружает пользователей, отделы и настройки независимо: ошибка одного блока не скрывает остальные. Настройки отправляются полным `PUT /api/admin/settings`, включая часовой пояс и квоту обновлений. Общий лимит переводится из рублей в целые копейки; пустое поле означает `null`, ноль сохраняется как `0`.

Квота обновлений — целое число от 0 до 100 согласно API. Сохранение настроек и их загрузка после перезагрузки проверены на настоящем backend.

API пользователей возвращает `is_active`; таблица показывает «Активен» или «Отключён». Для совместимости со старым API без этого поля сохранена защита: «Не указан» и отсутствие изменения статуса при обычной правке сотрудника. Исправление backend и результаты повторной проверки записаны в [QA админки](artefacts/tests/qa-admin.md).

```bash
npm run lint
npm run format:check
npm test
npm run build
npx playwright install chromium
npm run test:e2e
```

На Windows можно использовать уже установленный Edge:

```powershell
$env:PLAYWRIGHT_CHANNEL='msedge'
npm run test:e2e
```

Playwright сам запускает Vite на 5173 или использует уже запущенный сервер на этом порту. Проверяет desktop Chromium и мобильный viewport 390×844 в Chromium (это не тест Safari). Трассы и снимки ошибок сохраняются в `frontend/test-results/` и не коммитятся.

Если Vite уже работает на другом порту, задайте `PLAYWRIGHT_BASE_URL` (например, `http://127.0.0.1:5174`): тесты используют этот сервер без запуска и остановки своего процесса.
