## Исправлено в нашей части

- Frontend принимает типизированный `CutoffResult`; демо возвращает тот же контракт.
- `sync=ok` сообщает об обновлённых ценах; `sync=skipped` предупреждает об использовании сохранённого каталога. `already_closed=true` сообщает о повторном закрытии без ложной ошибки Mealty.
- Live-тест сохраняет проверку `dish_id`, `qty`, `planned_price_kopecks`, допускает изменение фактических цен и доступности после job. Для рассчитанного плана проверяет фактическую сумму без снятых блюд.
- В тесте обработки ошибок job зафиксированы часы: он больше не зависит от календарной даты запуска.
- Параллельный серверный тест дожидается обеих задач даже при исключении. Ошибка backend продолжает проваливать тест, но не оставляет задачу работать во время очистки таблиц.

## QA-CUTOFF-01 — новый план после досрочного закрытия

**Статус:** открыт. **Приоритет:** высокий. **Ответственный за исправление:** backend.

**Предусловия:** дата доставки через 30 дней, обычный дедлайн не наступил. Сотрудник A сохранил одну позицию, у сотрудника B плана нет.

**Шаги:**
1. Закупки вызывают `POST /api/orders/{date}/cutoff` → 200, заказ закрыт.
2. Сотрудник B вызывает `GET /api/plans/{date}`.
3. Сотрудник B отправляет `PUT /api/plans/{date}` с одной позицией.

**Ожидание:** `editable=false`, PUT → 403, согласно [контракту ручного cutoff](../../api.md).

**Факт:** GET возвращает `editable=true`, PUT → 200. Новый план появляется после фиксации общего заказа и не включается в уже созданный снимок.

**Причина по коду:** проверка редактирования учитывает время и статус личного плана, но не наличие закрытого общего заказа. Frontend следует серверному `editable`.

**Воспроизведение:** после подготовки тестового контейнера по [инструкции](../../../tests/README.md):

```powershell
docker compose --env-file tests/.env.test exec -T api python -m pytest -q tests/test_orders_cutoff.py -k new_employee --runxfail
```

В обычном регрессе тест отмечен `xfail(strict=True)` с идентификатором дефекта. Это ожидаемый сбой, не PASS. После исправления backend успешное выполнение даст XPASS(strict), и отметку нужно снять. [Первичное воспроизведение](qa-evidence/cutoff-2026-10-16/cutoff-first.xml): 8 passed, 1 failed.

## QA-CUTOFF-02 — гонка первичного создания настроек

**Статус:** открыт, проявление зависит от порядка выполнения запросов. **Ответственный за исправление:** backend.

На пустой тестовой базе два одновременных cutoff вызывают создание singleton-настроек. В первом полном прогоне `test_concurrent_cutoffs_create_exactly_one_order` упал с `UniqueViolationError: settings_pkey`: обе сессии попытались вставить строку `id=1`. В `get_or_create_settings` последовательность SELECT → INSERT не защищена от такого соревнования.

Ожидается успешная обработка обоих вызовов с одним общим заказом. Воспроизведение: `pytest -q tests/test_orders_service.py::test_concurrent_cutoffs_create_exactly_one_order`; единичный успешный прогон не опровергает гонку.

Первый прогон также дал ошибку очистки и последующий сбой квоты: параллельная задача продолжала работать после падения первой. Ожидание обеих задач исправлено в тесте; тест квоты отдельно прошёл. [Первый полный прогон](qa-evidence/cutoff-2026-10-16/backend-first-regression.xml) сохранён как доказательство, его каскадные сбои не считаются отдельными продуктовыми дефектами.
